# 장복인간 업무 규칙

기준일: 2026-11-07. 지금까지 확정한 요구사항과 현재 구현을 정리한 문서다. 규칙을 변경할 때 이 문서를 함께 수정한다. 실행 방법은 [README](../README.md)를 참고한다.

## 1. 서비스와 용어

- 화면의 서비스 이름은 **장복인간**, 프로젝트 이름은 `workshare`, Java 기본 패키지는 `com.jangbokhuman.workshare`다.
- 복지관 직원의 휴가·업무 선호·다른 업무 지원을 반영해 날짜별 업무를 배정한다.
- 직원 수와 활동 참여 인원에 **5명 같은 고정 정원을 두지 않는다**. 입사·인원 제외에 따라 인원이 늘거나 줄 수 있다.
- **활동**은 나눔가게 활동처럼 독립적인 업무 영역이다. 종류·이름·설명은 `Activity` enum으로 정의하며 활동 마스터 테이블을 두지 않는다. 새 활동과 동작은 개발자가 코드로 추가한다.
- **업무**는 특정 활동의 특정 날짜에 수행할 일이다. 나눔가게의 기본 오전·오후 업무 외에 같은 날 여러 업무가 추가될 수 있다. 다른 활동이 오전·오후 업무를 가진다고 가정하지 않는다.
- 직원 프로필의 **담당 업무**는 관리자가 지정하는 복수 선택 정보다. 이 목록을 선택하는 것과 날짜별 지원표를 작성하는 것은 별개다.
- **직군**과 로그인 권한(`STAFF`, `ADMIN`)은 별개다.

## 2. 계정·프로필·권한

### 직원 계정

- 관리자가 직원 계정을 만든다. 직원이 직접 회원가입하는 기능은 제공하지 않는다.
- 한글 이름 하나를 로그인 이름과 표시 이름으로 함께 사용한다. 별도 영문 아이디는 받지 않는다.
- 로그인 시 이름으로 계정을 찾은 뒤 직원 ID를 인증 세션에 보관한다. 이후 본인 휴가·선호도·프로필·지원일 교환은 세션의 직원 ID로 처리한다. 직원용 요청에서 받은 이름이나 직원 ID로 본인을 결정하지 않는다. 관리자는 별도 관리자 경로에서 대상 직원 ID를 선택한다.
- 새 이름은 공백 없는 한글 1~30자다. 이름 중복은 DB 고유 제약으로 막으며 동명이인을 중복 등록할 수 없다.
- 새 직원 비밀번호는 8~20자다. 영문 대소문자·숫자·특수문자 `!@#$%_-`를 허용한다. 모든 문자 종류를 반드시 섞도록 강제하지는 않는다.
- 비밀번호는 BCrypt 해시로 저장한다. 눈 아이콘은 **입력 중인 비밀번호**만 보여주며 저장된 비밀번호를 조회하는 기능이 아니다.
- 직원 본인은 내 프로필에서 현재 비밀번호를 입력한 뒤 비밀번호를 바꿀 수 있다. 새 비밀번호에는 직원 등록과 같은 입력 규칙을 적용한다.

### 직군과 담당 업무

직군은 다음 중 **하나만** 선택한다.

직군은 `WorkGroupType` enum으로 정의한다. 직원의 현재 직군에는 enum을 직접 저장하고 활동별 직군 제한도 코드에서 enum으로 비교한다. 별도 직군 마스터 테이블이나 DB 참여 허용 규칙을 두지 않는다. 직원 직군은 한 개이며 변경 시 즉시 덮어쓴다. 직군 변경 이력은 보관하지 않고 확정된 배정 결과는 유지한다.

| 직군 | 내부 코드 |
| --- | --- |
| 식당 | `RESTAURANT` |
| 운영지원 | `GENERAL` |
| 운영지원(기계실) | `FACILITY_SUPPORT` |
| 3층 | `THIRD_FLOOR` |
| 발달지원 | `DEVELOPMENT_SUPPORT` |

- 담당 업무는 등록된 목록에서 여러 개 선택할 수 있다. 선택할 업무 목록도 관리자가 관리한다.
- 직군·담당 업무 변경은 **관리자 직원 상세 화면에서만** 제공한다. 본인 프로필이라고 직원이 바꿀 수 있는 것은 아니다.
- 일반 프로필은 관리자에게도 직군·담당 업무를 조회만 허용한다.
- 프로필 사진은 본인 또는 관리자가 등록한다. JPG·PNG 2MB 이하의 실제 이미지만 받고, 최대 512px JPEG로 변환해 저장한다.
- 인원 제외 후에도 직원과 과거 배정의 연결을 보존한다.

### 관리자 화면 분리

- 관리자와 직원 모두 로그인 성공 후 일반 나눔가게 카드 화면(`/sharing-shop`)으로 이동한다.
- 로그인 전에 `/admin`을 열었더라도 로그인 후 관리자 화면으로 자동 이동하지 않는다.
- 일반 화면에는 관리자 메뉴·진입 링크·권한 배지를 노출하지 않는다.
- 관리자 화면은 **`/admin` 주소를 직접 입력**해서 접근한다.
- `/admin`과 `/admin/**`는 서버에서 `ADMIN` 권한을 검사한다. 로그인한 직원이 직접 URL 또는 변경 요청을 보내도 **403**으로 차단한다.
- 로그인하지 않은 사용자는 로그인 화면으로 안내한다. 인증되지 않은 REST 요청은 401이다.

| 기능 | 직원 | 관리자 |
| --- | --- | --- |
| 일반 활동 카드·직원 프로필 조회 | 가능 | 가능 |
| 본인 휴가·선호도 입력 | 가능 | 직원용 입력 기능 사용 안 함 |
| 다른 직원 휴가 입력 | 불가 | 관리자 화면에서 가능 |
| 직군·담당 업무 변경 | 불가 | 관리자 화면에서 가능 |
| 본인 사진 등록 | 가능 | 관리자 화면에서 직원 사진 등록 가능 |
| 월별 지원표·필요 인원·제외 사유 관리 | 불가 | 가능 |
| 본인 지원일 교환 요청·받은 요청 수락 | 가능 | 직원용 교환 기능 사용 안 함 |
| 휴일 관리 | 불가 | 가능 |

## 3. 날짜와 마감 시각

모든 날짜와 시각은 **한국 시간 `Asia/Seoul`** 기준이다. 마감 시각은 지원일·업무일 **당일** 기준이며, 전날이 아니다.

| 항목 | 변경·실행 기준 |
| --- | --- |
| 직원 본인·관리자 대리 휴가 입력 | 해당 날짜 **08:49 전** |
| 나눔가게 시간대 선호도 변경 | 날짜별 마감 없음. 다음 추첨부터 반영 |
| 당일 휴일 추가·해제 | 해당 날짜 **08:49 전** |
| 직원 등록·인원 제외의 당일 적용 | **08:49 전**, 이후 변경은 다음 날부터 적용 |
| 직원 직군 변경 | 현재 직군 한 개를 즉시 덮어씀. 확정 배정은 유지 |
| 활동 가입·탈퇴 | 즉시 반영. 이미 확정된 배정은 유지 |
| 날짜별 지원표 변경·지원일 교환 요청/수락 | 해당 날짜 **08:50 전** |
| 지원 필요 인원 변경의 당일 적용 | **08:50 전**, 이후 변경은 다음 날부터 적용 |
| 기본 업무 자동 배정 | 근무일 **08:50** |
| 날짜 카드의 배정 결과 조회 시작 | 해당 날짜 **08:50:10** |
| 만료된 지원일 교환 요청 삭제 | 매일 **09:00** |

- **08:49:00부터** 해당 날짜의 휴가를 변경할 수 없다. **08:50:00부터** 지원표 변경·교환 수락을 할 수 없다.
- 예: 11월 10일 업무의 휴가는 11월 10일 08:49 전, 지원표와 교환 수락은 11월 10일 08:50 전까지다.
- 미래 날짜의 휴가·지원표를 미리 입력할 수 있다.
- 배정은 당일 08:50 이후에만 실행한다. 휴가 입력은 해당 날짜의 08:49 마감 시각으로 판단한다. 직원별 나눔가게 시간대 선호도는 별도로 유지한다.
- 설정 변경의 적용일과 과거 배정 기록은 구분한다. 설정 변경으로 확정된 결과를 다시 추첨하지 않는다.

## 4. 근무일과 휴일

- 토요일·일요일은 자동 휴무다. 휴가 신청과 업무 배정을 하지 않는다.
- 관리자가 별도 휴일을 추가하거나 해제할 수 있다. 휴일 사유는 **선택 입력**이다.
- 휴일 달력에서 등록된 휴일은 빨간색으로 표시한다.
- 휴가 신청이 있는 날짜를 휴일로 바꾸어도 기존 신청은 보관한다. 휴일을 해제하면 기존 신청을 다시 적용한다.
- 토·일요일은 별도 휴일 등록을 해제해도 휴무다.

## 5. 출근·휴가·반차

| 입력 상태 | 오전 업무 · 09:00~14:00 | 오후 업무 · 14:00~18:00 |
| --- | --- | --- |
| 정상 출근 / 미입력 | 배정 가능 | 배정 가능 |
| 연차 | 배정 제외 | 배정 제외 |
| 병가 | 배정 제외 | 배정 제외 |
| 오전 반차 | 배정 불가 | 배정 가능 |
| 오후 반차 | 배정 가능 | 배정 불가 |

- 오전 반차와 오후 반차를 구분한다. `Attendance`에 오전·오후 결근 여부를 두고 시간대별 배정 가능 여부를 판단한다. 종일 결근 여부는 두 시간대 모두 결근인지로 계산한다.
- 휴가 상태는 **직원 + 날짜** 단위로 저장하고 모든 활동에 공통 적용한다.
- 직원은 자신의 일정만 입력한다. 다른 직원의 이름이나 ID를 요청에 넣어도 입력 대상은 로그인한 본인이다.
- 직원 조회는 Repository에서 수행하고 `LeaveRequestValidator`가 신청 마감·주말/휴일·요청 날짜의 직원 근무 기간을 검증한다. 이미 등록된 휴가는 변경·취소를 막는 조건이 아니다.
- 관리자는 직원을 선택해 연차·병가·반차를 대신 입력할 수 있다. 직원과 동일한 날짜·마감·근무 기간 조건을 적용한다.
- 휴가 취소는 해당 날짜를 **정상 출근**으로 저장한다. 별도 휴가 사유는 수집하지 않는다.
- 본인과 관리자는 같은 신청 엔티티를 조회·수정해 저장한다. 최초 등록이 겹치면 DB 고유 제약으로 중복을 막으며 한 요청은 실패할 수 있다. 실패한 요청은 새로고침 후 다시 저장한다. 별도 전역 락이나 자동 재시도는 두지 않는다.
- 오전 반차자는 오후, 오후 반차자는 오전에만 배정할 수 있다. 기계실 상주를 맡은 시간대는 나눔가게 후보에서 빠진다.

## 6. 나눔가게 참여 인원 산정

배분의 기준은 전체 직원 수가 아니라 **그날 해당 활동에 실제 배정 가능한 인원**이다.

1. `ActivityRegistration`에 등록된 직원 중 해당 날짜가 직원의 근무 기간에 포함되는 대상을 조회한다.
2. 가입할 때 필수 등록 제한을 검사한다. **식당 직군은 나눔가게에 가입할 수 없다.** 직원 관리 화면에서 직군별 자동 탈퇴 대상을 미리 안내한다. 직군 변경으로 가입 자격이 사라지면 가입과 선호도를 같은 트랜잭션에서 정리하고, 저장 결과에 탈퇴한 활동을 표시한다.
3. 해당 날짜의 식당지원·외부 업무 등 다른 업무로 제외된 직원을 뺀다.
4. 연차·병가 직원을 뺀다. 오전·오후 반차자는 자신이 근무 가능한 시간대의 후보로 남긴다.
5. 남은 인원수로 오전·오후 배분 기준을 찾는다.

- 직군이 미지정이거나 활동 참여 자격이 없는 직원은 배정하지 않는다.
- 다른 업무로 인한 제외는 지정된 **활동 + 날짜**에만 적용한다. 영구적인 활동 명부를 바꾸지는 않는다.
- 직원 계정 등록만으로 활동에 자동 가입하지 않는다. 관리자가 활동 상세 화면에서 직원별 `+`로 가입시키고 `−`로 탈퇴시킨다. 요청은 해당 직원 한 명에게 적용한다. 활동·직원당 가입 한 건만 저장하며 가입·탈퇴는 즉시 반영한다. 휴가·당일 지원은 가입을 해제하지 않는다.
- 식당에서 다른 직군으로 돌아와도 나눔가게에 자동 재가입하거나 이전 선호도를 복구하지 않는다.
- 활동 참여 불가와 일반 화면 조회 권한은 별개다. 식당 직군도 로그인·본인 휴가 입력·일반 화면 조회는 가능하다.
- 기계실은 오전·오후 각각 상주 한 명이 필요하다. 실제 출근자가 한 명 이상 남는 조합을 우선하며, 불가능하면 나눔가게에 배정하고 해당 시간대에 기계실 인원 부족을 경고한다. 기계실 등록 인원이 0명인 경우에도 경고한다.
- 기본 업무와 추가 업무의 자동 배정은 같은 제외 조건을 적용한다.

예: 나눔가게 담당자 5명 중 식당지원 2명이면 배분 기준 인원은 **3명**이다. 식당지원 2명을 뺀 뒤 상주 담당을 다시 한 명 빼지 않는다.

## 7. 오전·오후 배분과 선호도

### 배분 기준

- `application.yml`의 `app.sharing-shop-quotas`에 **가능 인원수별 오전·오후 인원**을 설정한다. 앱을 다시 실행하면 예정 인원과 다음 추첨에 적용된다. [설정 예시](../README.md#나눔가게-오전오후-배분)
- 2명 이상에 대한 설정은 오전·오후 인원 합계가 가능 인원과 같아야 한다. 한 시간대 인원을 0명으로 정할 수도 있다.
- 설정하지 않은 인원수는 다음 기본값을 사용한다.

| 실제 가능 인원 | 오전 기본 인원 | 오후 기본 인원 |
| --- | --- | --- |
| 0명 | 0명 | 0명 |
| 1명 | 같은 직원 1명 | 같은 직원 1명 |
| 2명 | 1명 | 1명 |
| 3명 | 2명 | 1명 |
| 4명 | 2명 | 2명 |
| 5명 | 3명 | 2명 |
| 6명 | 3명 | 3명 |

- 2명 이상의 기본값은 오전 `ceil(가능 인원 / 2)`, 오후는 나머지다.
- **1명이고 정상 출근이면 오전·오후를 모두 맡는다.** 1명이 반차자라면 근무 가능한 시간대만 배정하고 반대 시간대의 부족을 표시한다.
- 오전·오후의 기계실 상주 후보를 정하고, 각 조합에서 남은 직원의 나눔가게 배정을 계산한다. 비는 나눔가게 시간대, 기계실 상주 부족, 겸임, 미배정 인원, 목표 비율 순으로 비교한다.
- 예: 3명이 모두 오전만 가능하면 오전 3명·오후 0명으로 배정하고 오후 인원 부족을 경고한다. 7명 중 6명이 오전만 가능하고 한 명이 종일 가능하면 오전 6명·오후 1명으로 배정한다.
- 기계실 직원 두 명 중 한 명이 오후 반차이고 두 명 모두 나눔가게 담당이면, 오후 반차자는 오전에, 종일 근무자는 오후에 배정하고 오후 기계실 인원 부족을 경고한다.
- 배정 가능자가 기계실 반차자와 다른 직군 종일 근무자 두 명뿐이고, 반차자가 출근하는 시간대의 유일한 기계실 직원이라면 그 직원은 기계실에 남고 종일 근무자가 나눔가게 오전·오후를 맡는다. 반대 시간대에 기계실 출근자가 없으면 해당 시간대 상주 부족을 경고한다.
- 위 두 사람이 모두 오전만 가능하면 다른 직군 직원이 오전 나눔가게를 맡고 기계실 직원은 상주한다. 오후에는 나눔가게와 기계실 부족을 각각 경고한다.

### 나눔가게 시간대 선호도

- 나눔가게의 오전·오후 업무에만 사용하는 전용 설정이다. 모든 활동의 공통 선호도로 일반화하지 않는다.
- `SharingShopTimePreference`에 **직원별 하나**를 저장한다. 서비스 저장 인자는 직원 ID와 시간대 선호도이며 날짜·시각·활동 코드는 받지 않는다.
- 나눔가게 화면에서 변경하며 날짜가 바뀌어도 계속 유지한다. 변경은 다음 추첨부터 반영하고 이미 확정된 배정의 스냅샷은 유지한다.
- 날짜별 입력 마감이 없으며 주말·휴일·휴가·당일 지원 중에도 변경할 수 있다. 식당 직군 등 나눔가게 참여 자격이 없는 직원은 저장할 수 없다.
- 선호도 변경 권한은 `SharingShopTimePreferenceChangePolicy.evaluateChangePermission()`으로 판단한다. 나눔가게에 가입한 직원은 근무 시작 전에도 변경할 수 있다. 선호도 변경은 가입 여부와 현재 비활성 여부를 확인한다. 직군별 등록 제한은 가입·직군 변경 시 처리한다.
- 선호도 변경에는 배정 마감·근무 시작일·활동 시작일을 적용하지 않는다. 실제 날짜의 근무 기간과 가입 여부는 `DailyActivityParticipationPolicy.evaluateEligibility()`에서 확인하고, `evaluateAvailability()`는 해당 날짜의 지원 제외 여부까지 확인한다. 검사 날짜를 미래로 보정하지 않는다.
- 선택지는 오전 선호·오후 선호·무관이다. 미입력은 무관이다.
- 운영 조건과 목표 비율이 같은 조합 중 선호를 가장 많이 만족시키며, 동률이면 기본 방향을 우선한다.
- 조건이 같은 후보끼리는 무작위로 선택한다. 먼저 선호를 입력했다고 우선하지 않는다.
- 기본 비율이 3대2여도 오전 선호 2명·오후 선호 3명이면 오전 2명·오후 3명으로 배정할 수 있다. 같은 조건의 후보 사이에서는 추첨한다.
- 선호도는 참여 제한을 무시하는 강제 지정이 아니다. 오후 반차자의 오후 선호와 오전 반차자의 오전 선호는 충족할 수 없다.
- 당일 지원자는 추첨 대상에서 제외하지만, 직원별 시간대 선호도 설정은 계속 유지·변경할 수 있다. 다른 활동에는 이 선호도를 적용하지 않는다.
- 날짜별 추첨이다. 장기간 같은 횟수를 보장하는 순번제나 누적 공정성 규칙은 현재 없다.

## 8. 월별 지원표와 제외 사유

- 식당지원은 기본 기준이 **하루 2명**이다. 관리자는 필요 인원 기준과 별개로 날짜마다 실제 지원자 수를 선택할 수 있다.
- 관리자는 매달 전달받은 지원표를 날짜별로 직접 입력하고 월 단위로 저장한다. 식당지원 담당자를 자동 추첨하지 않는다.
- 식당지원 외에도 제외 사유를 추가할 수 있다. 새 사유 때문에 나눔가게 추첨 코드에 조건문을 계속 추가하지 않는 구조로 관리한다.
- 식당지원에는 해당 날짜에 근무하는 식당 외 직군을 등록할 수 있다. 나눔가게는 식당지원표를 읽고 당일 지원자를 오전·오후 배정에서 제외한다.
- 같은 직원의 같은 활동·같은 날짜에는 여러 지원을 중복 등록할 수 없다.
- 활동별 제외 사유는 해당 활동의 참여 자격을 확인한다. 종일 지원은 연차·병가·반차가 없는 직원에게 배정한다.
- 나중에 휴가를 입력해 기존 지원과 충돌하면 경고한다. 지원표 수정이나 교환으로 조정하며, 기존 휴가를 임의로 취소하지 않는다.
- 실제 지원 인원이 기준과 다르면 안내를 표시하고 입력한 명단을 저장한다.
- **지원표가 비어 있으면 특정 직원을 임의로 제외하지 않는다.** 실제 등록된 지원자만 제외하고 미입력 경고를 표시한다.
- 필요 인원 설정만 바꿔도 기존 지원 명단을 자동 증감하지 않는다. 관리자가 명단을 함께 확인한다.
- 과거 날짜·당일 08:50 이후·배정이 확정된 날짜의 지원표는 변경하지 않는다.

## 9. 직원 간 지원일 맞교환

교환은 한 날짜의 대타 지정이 아니라 **두 직원의 서로 다른 지원 날짜를 맞바꾸는 방식**이다.

예: 홍길동의 11월 10일 식당지원과 김민수의 11월 11일 식당지원을 교환하면, 수락 후 김민수가 11월 10일, 홍길동이 11월 11일을 맡는다. 두 날짜의 지원 인원수는 유지한다.

1. 직원이 자신의 지원일을 고른다.
2. 같은 지원 업무를 맡은 다른 직원의 다른 지원일을 고른다. 두 직원이 실제로 맡을 수 있는 일정만 후보로 보여준다.
3. 상대 직원에게 교환 요청을 보낸다. 상대 직원은 앱의 **받은 교환 요청**에서 확인한다.
4. 수락 전에는 기존 지원표와 활동 제외 인원을 유지한다.
5. 요청받은 직원이 수락하면 두 날짜의 담당자를 하나의 트랜잭션으로 함께 변경한다.

### 권한과 재검사

- 본인의 지원일만 요청할 수 있다. 타인의 지원일로 요청을 만들 수 없다.
- 요청받은 직원만 수락할 수 있다. 제3자가 요청 ID를 알아도 수락할 수 없다.
- 보낸 직원은 취소하고, 받은 직원은 거절할 수 있다.
- 수락 시 마감·현재 담당자·활동 자격·근무 기간·휴가/반차·다른 지원 중복을 다시 검사한다.
- 요청 후 관리자가 해당 배정을 바꾸었거나 다른 교환으로 이미 바뀌었다면 기존 요청을 적용하지 않는다.
- 교환이 성사되면 두 지원 일정에 걸린 다른 요청을 함께 정리해 중복 교환을 막는다.
- 동시에 수락 요청이 들어와도 한 번만 반영한다.

### 마감과 정리

- 두 지원 날짜 중 **이른 날짜의 당일 08:50**이 요청 만료 시각이다.
- 예: 11월 10일과 11월 11일 교환은 11월 10일 08:50 전까지 수락해야 한다.
- 만료 시각부터는 DB 정리 실행 여부와 관계없이 수락할 수 없고 요청함에도 표시하지 않는다.
- 매일 한국 시간 **09:00**에 스케줄러가 만료 요청을 DB에서 삭제한다. 지원표 자체는 삭제하지 않는다.
- 교환으로 확정된 과거 나눔가게 배정을 수정하지 않는다.

## 10. 업무 배정과 기록 보존

- 한 날짜에 오전·오후 기본 업무와 여러 추가 업무가 존재할 수 있다. 날짜 하나가 업무 하나를 의미하지 않는다.
- 오전·오후 기본 업무는 함께 추첨한다. 추가 업무는 업무별 시간대·필요 인원에 따라 별도로 배정한다.
- 한 사람이 여러 업무를 맡을 수 있다. 현재 추가 업무 사이의 시간 겹침을 자동으로 금지하는 규칙은 없다.
- 미래 추가 업무는 당일 08:50에 배정한다. 당일 08:50 이후 추가한 업무는 가능한 직원 중 즉시 배정한다.
- 추가 업무의 취소 처리는 **배정 대기 상태**에만 적용한다.
- 확정된 업무를 재추첨·취소하지 않는다. 직원·명부·설정 변경과 새 업무 추가로 기존 결과를 덮어쓰지 않는다.
- 배정 당시 직원 ID·이름·출근 상태는 업무의 배정 기록으로 보관한다. 시간대 선호도는 나눔가게의 직원별 설정으로 관리한다.
- 매일 08:50과 앱 기동 시에만 자동 배정을 확인한다. 기동 시각이 08:50 이후이면 당일 누락 배정을 처리하고 이미 확정된 업무는 유지한다.
- 기동 중 자동 배정에서 예외가 발생하면 앱 기동을 실패 처리한다.

## 11. 화면과 결과 공개

- 휴대폰을 주 화면으로 하는 반응형 웹이다. 장복인간 이름과 복지관 업무 배정 앱이라는 설명을 사용한다.
- 일반 직원과 관리자 화면 모두 햄버거 메뉴로 기능을 이동한다. 모든 관리 기능을 한 페이지에 길게 나열하지 않는다.
- 나눔가게 활동은 달력 대신 **가로로 넘기는 날짜 카드**다. 진입 시 오늘 카드가 가운데 온다.
- 배정 전에는 참여 직원·휴가 직원·다른 업무로 제외된 직원, 오전·오후 예정 인원과 카운트다운을 표시한다.
- 스케줄러는 08:50에 추첨한다. 화면은 **08:50:10부터 REST로 저장된 결과를 조회**한다. 아직 준비되지 않았다면 다시 조회한다.
- 결과 조회 자체가 추첨을 실행하지 않는다. 이미 DB에 배정이 있어도 08:50:10 전에는 카드에서 공개하지 않는다.
- 휴가 입력은 별도 월별 달력에서 로그인한 본인의 일정을 대상으로 한다.
- 관리자 활동 화면은 enum의 활동을 앨범처럼 표시하고 담당 직원을 관리한다. 이름·설명은 enum에서 조회한다. 활동 추가·설명 편집·직군별 참여 허용/금지 토글은 제공하지 않는다.

## 12. 구현·확장 원칙

- Spring 단일 웹 서버, Thymeleaf, Spring Security를 사용한다. 운영 DB는 Docker MySQL이며 H2는 테스트에서만 사용한다.
- 실행 설정은 `application.yml` 하나로 관리한다. 스케줄러는 항상 동작하며 기능 비활성화용 조건을 두지 않는다.
- Spring 서비스는 조정과 트랜잭션을 담당하고, 순수 배분 정책은 Spring·JPA·웹 세션에 의존하지 않는다.
- 명부·날짜별 제외·필요 인원·배분 기준·교환 동의를 서로 다른 책임으로 분리한다.
- 단순한 제외 사유 추가는 데이터로 처리한다. 별도의 참여 제한 로직이 필요하면 제한 정책을 확장한다.
- 직원 이름 중복은 DB 고유 제약으로 처리한다. 직원 등록에 정원 검사나 이를 위한 전역 락을 넣지 않는다.
- 앱 전체의 전역 락이나 활동 잠금용 테이블은 사용하지 않는다. 휴가·선호도는 JPA 조회·변경·`save()`를 사용한다. 가입·직군·선호도 변경은 직원 행, 지원표·교환은 지원 사유·요청 행, 대기 업무 배정·취소는 업무 행을 잠근다. 자동 업무 생성은 활동·날짜·코드 고유 제약으로 중복 저장을 막는다. 구체적인 범위는 [동시 저장과 잠금 기준](concurrency.md)을 따른다.
- 활동 종류·가입·공통 업무는 `activity`에, 나눔가게 오전·오후 배정과 시간대 선호도는 `activity.sharingshop`에 둔다. 나눔가게의 오전·오후 생성은 `SharingShopDailyAllocator`에서 처리한다. 새 활동의 자동 업무는 해당 활동의 `DailyActivityAllocator` 구현으로 추가한다.
- 날짜와 시각 판단은 주입한 `Clock`을 사용한다. 로거는 `@Slf4j`를 사용한다.
- Java 소스와 테스트에서는 `var`를 사용하지 않는다. 지역 변수·반복문·try 자원 선언 모두 명시적인 타입을 작성한다.
- 엔티티의 단순 getter는 Lombok `@Getter`로 생성한다. 컬렉션·이미지의 방어적 복사가 필요한 조회 동작은 별도 메서드로 유지한다.
- 자동 생성 대리키는 `Long`과 `@GeneratedValue(strategy = GenerationType.IDENTITY)`를 사용한다. 휴일 날짜, 담당 업무 제목 같은 자연키와 직원 사진의 공유 직원 키는 별도 자동 생성하지 않는다. 직군과 활동 종류는 enum으로 저장한다.
- 개발 단계에서는 초기 스키마를 직접 수정하고 로컬 개발 DB를 초기화한다. 데이터 보존용 버전별 이관과 `legacy_*` 열은 추가하지 않는다. MySQL과 H2 테스트 스키마를 함께 갱신한다.
- 단순 주입 생성자는 Lombok `@RequiredArgsConstructor`를 사용한다. JPA 기본 생성자는 `@NoArgsConstructor(access = AccessLevel.PROTECTED)`로 작성하며, 검증·초기화·값 복사가 있는 생성자는 명시적으로 유지한다.
- 주입 필드는 타입과 역할을 명확하게 이름에 담는다. 예를 들어 `LeaveRequestRepository leaveRequestRepository`, `WorkQueryService workQueryService`, `WorkTime workTime`으로 작성하고 `requests`, `queries`, `time` 같은 축약 주입 필드명은 사용하지 않는다. 테스트의 주입 필드도 같은 원칙을 적용한다.

## 13. 논의했지만 아직 적용하지 않은 항목

로그인하면 같은 브라우저에서 90일 동안 자동 로그인을 사용한다. 서버 세션은 마지막 요청 후 30분 동안 사용하지 않으면 만료되지만, 유효한 자동 로그인 쿠키가 있으면 새 세션을 만든다. 로그아웃하면 해당 브라우저의 자동 로그인 쿠키를 지운다. 직원 비밀번호가 바뀌면 기존 자동 로그인 쿠키가 무효화된다. 관리자 계정은 앱 재시작 후 다시 로그인한다.
