# 동시 저장과 잠금 기준

기준일: 2026-11-07. 활동은 enum이며 활동 테이블·전역 잠금 테이블은 두지 않는다. 필요한 실제 업무 행만 잠근다.

## 저장과 잠금

| 작업 | 처리 | 보장하는 내용 |
| --- | --- | --- |
| 휴가 저장 | 엔티티 조회·변경 후 Repository `save()`, 직원·날짜 고유 제약 | 중복 행을 막는다. 최초 저장 경합에서는 한 요청이 충돌할 수 있다. |
| 나눔가게 선호도 저장 | 해당 `Employee` 행 잠금 | 가입 확인·저장을 직군 변경·탈퇴와 조정해 선호도만 다시 생기는 것을 막는다. |
| 활동 가입·탈퇴 | 요청 대상 직원 한 명의 행 잠금 | 같은 직원의 가입·탈퇴·직군 변경을 조정한다. 활동·직원 고유 제약을 유지하고 반복 가입은 같은 가입 ID를 사용한다. |
| 자동 배정 | 실행별 트랜잭션과 업무의 활동·날짜·코드 고유 제약 | 같은 업무를 두 호출이 동시에 생성하면 한 실행만 저장되고 충돌한 트랜잭션은 롤백된다. |
| 대기 업무 자동 배정·취소 | 해당 `WorkTask` 행 잠금 | 같은 대기 업무의 중복 배정·배정 후 취소를 막는다. |
| 지원표·지원 필요 인원 변경 | 해당 `ExclusionReason` 행 잠금 | 같은 지원 업무의 명단·필요 인원 변경을 조정한다. 다른 사유의 중복 지원은 활동·날짜·직원 고유 제약으로 막는다. |
| 지원일 교환 요청·수락 | 해당 `ExclusionReason` 행, 수락 시 해당 교환 요청 행도 잠금 | 같은 지원 업무의 관리자 수정·교환 수락을 조정한다. |
| 교환 요청 취소·거절 | 해당 교환 요청 행 잠금 | 수락·삭제와 같은 요청을 동시에 처리하지 않는다. |
| 직원 직군·인원 제외·담당 업무 변경 | 해당 `Employee` 행 잠금 | 같은 직원의 정보 변경과 가입 정리를 하나의 트랜잭션으로 처리한다. |
| 휴일 변경 | 날짜 고유 키와 트랜잭션 | 휴일 변경 마감은 08:49, 당일 자동 배정은 08:50이므로 당일 추첨 이후 휴일 변경은 거절된다. |
| 만료 요청 정리 | 만료 조건이 있는 단일 DELETE | DB가 실제 삭제 행을 잠근다. |
| 일반 조회·직원 계정 등록 | 별도 명시적 잠금 없음 | 계정 이름 중복은 DB 고유 제약으로 처리한다. |

## 잠금 순서와 조회

- 가입·탈퇴는 직원 한 명을 대상으로 한다. 해당 직원 행을 잠근 뒤 가입 기록을 조회하고 변경한다.
- 직원 엔티티는 잠금을 얻은 후 읽는다. 잠금을 기다리는 동안 바뀐 직군 대신 영속성 컨텍스트의 이전 직군을 사용하는 것을 막는다.
- 직군 변경·선호도 저장도 해당 직원 행을 사용한다. 직군 변경 시 자격을 잃은 가입과 나눔가게 선호도를 같은 트랜잭션에서 삭제한다.
- 지원표와 교환 수락은 지원 사유 행을 먼저 잠그고, 수락은 교환 요청 행도 잠근다. 취소·거절은 요청 행만 잠근다.
- 지원 사유 ID를 알아내는 첫 조회는 스칼라 ID만 조회한다. 잠금 전에 읽은 지원 엔티티를 재사용하지 않는다.
- 활동 관리의 조회에는 읽기 전용 트랜잭션을, 가입·탈퇴에는 기본 `@Transactional`을 사용한다. 가입 여부를 확인해 이미 가입한 직원의 재요청은 기존 기록을 사용하고, 이미 탈퇴한 직원의 삭제 요청은 완료된 것으로 처리한다.
- 지원표 등 별도로 `READ_COMMITTED`가 지정된 처리에서는 필요한 행 잠금을 얻은 후 상태·마감을 다시 검사한다.

## 자동 배정과 중복 생성

`WorkTaskService`는 한 트랜잭션에서 기존 배정을 확인하고 누락된 업무를 처리한다. 동시에 같은 업무를 만들면 DB 고유 제약이 중복 저장을 막는다. 충돌한 트랜잭션은 롤백되고 스케줄러가 오류를 기록한다.

나눔가게의 `SharingShopDailyAllocator`만 오전·오후 업무를 생성한다. 두 업무와 추가 업무는 같은 실행 트랜잭션에 저장된다. 뒤 호출은 확정된 업무를 건너뛰며, DB의 활동·날짜·코드 고유 제약은 무결성을 보장한다.

자동 업무의 생성은 각 활동의 `DailyActivityAllocator` 구현이 담당한다. 배정 대기 중인 기존 업무는 공통 배정 서비스가 처리한다.

## 검증

- `ConcurrencyFeatureTest`: 최초 저장 경합, ID 보존, 겹치는 맞교환.
- `ActivityRegistrationFeatureTest`: 가입과 식당 이동의 동시 처리, 선호도 정리, 확정 배정 보존.
- `ActivityAllocatorFeatureTest`: 전용 정책이 없을 때 암묵적인 오전·오후 업무를 만들지 않는지 검증.
- `MySqlLockingIT`: 실제 MySQL에서 JPA 최초 저장 경합·지원일 맞교환·가입 무결성을 검증. 별도 프로젝트 검증 DB를 사용한다.

개발 중 스키마 변경은 MySQL·H2 V1을 함께 수정하고 승인된 로컬 개발·검증 DB를 초기화한다.
